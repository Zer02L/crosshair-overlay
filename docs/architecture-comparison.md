# Архитектурный анализ: Монолитный процесс vs Client-Server / Daemon + IPC

В данном документе зафиксирован сравнительный анализ двух архитектурных подходов для проекта **Crosshair Overlay**:
1. **Текущая реализация (Монолит с общим состоянием в памяти):** единый бинарник, запускающий оверлей, веб-сервер и нативное GUI-окно в разных потоках через `Arc<SharedState>`.
2. **Клиент-Серверная архитектура (Daemon + IPC/API):** разделение на ультралегкий фоновый сервис (`crosshaird`) и независимые клиенты управления (нативное GUI-окно на ПК, мобильное приложение, веб-пульт).

---

## Архитектура 1: Monolithic Shared Process (Текущая реализация)

Все подсистемы (графический Wayland-слой, HTTP/SSE-сервер, окно настроек `egui`, файловый наблюдатель) объединены в одном процессе:

```
┌────────────────────────────────────────────────────────────────────────┐
│                        Единый процесс (crosshair-overlay)              │
│                                                                        │
│  [ Thread 1: Main ]  ────►  egui Settings Window (нативное окно)       │
│                                  │                                     │
│  [ SharedState ]     ◄───────────┼───────────► [ crosshair_config.json]│
│        ▲                         │                                     │
│        │ (Arc/Mutex)             │ (calloop channel)                   │
│        ▼                         ▼                                     │
│  [ Thread 2: Axum ]  ────►  [ Thread 3: Wayland Layer-Shell Overlay ]  │
│    (HTTP/SSE/Web)                                                      │
└────────────────────────────────────────────────────────────────────────┘
```

### Плюсы монолита:
* **Нулевой оверхед задержки (Zero Latency IPC):** передача нового конфига из `egui` в оверлей происходит через очередь в оперативной памяти (`calloop::channel`). Время реакции — доли микросекунды.
* **Удобство «из коробки» (Single-Binary UX):** пользователь скачивает один бинарник с GitHub Releases, запускает его кликом или из терминала — и сразу получает и оверлей, и окно настроек, и веб-сервер. Никаких зависимостей, сокетов или демонов.
* **Простая отладка и логирование:** все логи приложения выводятся в единый stdout/stderr поток.
* **Низкая когнитивная сложность кодовой базы:** не требуется описывать сетевой протокол взаимодействия между GUI и оверлеем, обрабатывать разрывы соединений, таймауты и проверку статуса сервиса.

### Минусы монолита:
* **Время компиляции и размер релиза:** графический стек GUI (`eframe`, `egui-wgpu`, `wgpu`, шейдерный компилятор `naga`) компилируется значительно дольше, а релизный бинарник весит ~18 МБ.
* **Привязка к главному потоку ОС (Main Thread Constraint):** оконные библиотеки (`winit`/`eframe`) жестко требуют инициализации и запуска цикла событий исключительно в главном потоке процесса. Из-за этого циклу Wayland Layer-Shell приходится работать во вторичном потоке.
* **Негибкость для автозагрузки в headless-режиме:** хотя поддержан флаг `--no-gui`, бинарник все равно содержит внутри весь код `egui` и WGPU.

## Архитектура 2: Client-Server / Daemon + IPC (Целевая модель)

Разделение системы на два или более независимых бинарника:
* **`crosshaird` (Daemon):** консольный фоновый процесс (Wayland Layer-Shell + Axum REST/SSE/WebSocket API + File Watcher).
* **`crosshair-gui` (Client):** независимое окно настроек (на `egui`, Slint или Webview), которое при запуске подключается к локальному API демона.
* **Мобильные клиенты / Web UI:** обращаются к тому же API по сети.

```
┌────────────────────────────────────────────────────────────────────────┐
│               ПК: Фоновый Демон (crosshaird / headless)                │
│                                                                        │
│  ┌────────────────────────┐         ┌───────────────────────────────┐  │
│  │   Wayland Overlay      │ ◄────── │ Встроенный контроллер / API   │  │
│  │   (Layer-Shell)        │ (канал) │ (Axum: HTTP REST + SSE / WS)  │  │
│  └────────────────────────┘         └───────────────▲───────────────┘  │
└─────────────────────────────────────────────────────┼──────────────────┘
                                                      │ (JSON / HTTP / WS / Unix Socket)
                   ┌──────────────────────────────────┴──────────────────────────────────┐
                   ▼                                                                     ▼
    ┌─────────────────────────────┐                                      ┌─────────────────────────────┐
    │  1. Нативный GUI-клиент ПК  │                                      │ 2. Мобильное приложение     │
    │  (crosshair-gui на egui)    │                                      │    (iOS / Android / PWA)    │
    │  Подключается к :4848       │                                      │    Подключается по Wi-Fi    │
    └─────────────────────────────┘                                      └─────────────────────────────┘
```

### Плюсы Client-Server / Daemon:

1. **Идеальная интеграция с Linux (Systemd User Service / Autostart):**
   * Демон `crosshaird` прописывается в `systemd --user` или автозагрузку Sway/Hyprland/KDE.
   * Он стартует вместе с графической сессией, не создавая лишних окон на экране, и сразу показывает прицел при запуске любой игры.
2. **Экстремальная легковесность демона:**
   * Демон не содержит WGPU, шейдеров и графических фреймворков.
   * Размер бинарника `crosshaird` уменьшается до **~2-4 МБ**.
   * Потребление оперативной памяти падает до рекордных **~4-6 МБ RAM**.
   * 0% нагрузки на CPU в игровом цикле.
3. **Полная независимость GUI от оверлея:**
   * Окно настроек можно запускать и закрывать когда угодно. При закрытии окна оверлей в игре не прерывается и не мерцает.
   * Если GUI-клиент зависнет или аварийно завершится, игровой оверлей продолжит стабильно функционировать.
4. **Унифицированный протокол для всех платформ:**
   * Десктопный GUI, веб-страница на смартфоне и нативное мобильное приложение (Android/iOS) работают через **один и тот же сетевой контракт** (REST / SSE / WebSocket).
5. **Возможность создания альтернативных фронтендов:**
   * Пользователи и мейнтейнеры могут писать любые клиенты управления: CLI-утилиту (`crosshairctl set color green`), апплет для системного трея (GNOME Shell Extension, KDE Plasmoid, Waybar-модуль) или интерфейс на Slint/Tauri.

### Минусы Client-Server / Daemon:

1. **Сложнее пользовательский сценарий первого запуска (UX):**
   * Вместо запуска одной программы пользователю нужно либо запускать два процесса вручную, либо инсталлировать systemd-юнит (`systemctl --user enable --now crosshaird`).
   * Если пользователь открыл GUI, а демон не запущен — нужно показывать экран ошибки с инструкцией по запуску.
2. **Сетевой оверхед (микрозадержка IPC):**
   * При передаче через локальный TCP loopback (`127.0.0.1`) или Unix Domain Socket появляется накладной расход на сериализацию/десериализацию JSON и сетевой стек ОС (порядка 0.1–0.5 мс). Для настройки статического прицела это незаметно, но это больше, чем наносекундный доступ в памяти.
3. **Обработка сетевых коллизий:**
   * Возможен конфликт портов, если порт `4848` уже занят другим приложением (требуется фолбэк на Unix Domain Socket или динамический выбор порта).
4. **Увеличение кодовой базы на синхронизацию:**
   * Клиенту GUI необходимо поддерживать постоянное соединение, обрабатывать обрывы сети, реконнекты и рассинхронизацию состояний при повторном подключении.

## Сводное сравнение

| Характеристика | Монолит (Текущая) | Client-Server (crosshaird + GUI) |
| :--- | :--- | :--- |
| **Количество бинарников** | 1 (`crosshair-overlay`) | 2 (`crosshaird` + `crosshair-gui`) |
| **Размер релизного бинарника** | ~18 МБ | Демон: ~3-4 МБ, GUI: ~15 МБ |
| **RAM демона в простое** | ~15 МБ | **~4-6 МБ** |
| **Запуск для новичка** | В 1 клик | Требует автозапуск / сервис |
| **Связь GUI и оверлея** | Жесткая (внутри процесса) | Слабая (через сокет/HTTP/SSE) |
| **Автозагрузка в Linux** | Возможна через `--no-gui` | Нативная (`systemd --user`) |
| **Устойчивость к крашам GUI** | Падает весь процесс | Оверлей продолжает работать |
| **Поддержка сторонних CLI/UI** | Ограничена Web API | Полная (любой клиент к демону) |

## Рекомендованный план перехода (Roadmap)

Текущая кодовая база спроектирована так, что переход во вторую схему не требует переписывания ядра:
1. **Шаг 1 (Выполнен):** В монолит добавлен флаг `--no-gui`, реализован `SharedState` и SSE-канал броадкаста изменений в реальном времени.
2. **Шаг 2 (Разделение Cargo Workspaces):**
   * Оформить корневой `Cargo.toml` с `[workspace]`.
   * Выделить `crates/crosshair-core` (рендер, Wayland Layer-Shell, конфиг).
   * Выделить бинарник `crates/crosshaird` (минималистичный демон без GUI-библиотек).
   * Выделить бинарник `crates/crosshair-gui` (клиент на `egui`, подключающийся по SSE/REST).
3. **Шаг 3 (Systemd & Packaging):**
   * Добавить готовый юнит `crosshaird.service` для каталога `~/.config/systemd/user/`.
   * Добавить desktop-файл `crosshair-gui.desktop` для меню приложений Linux.
